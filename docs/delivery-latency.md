# Immediate delivery and editable metadata updates (beta.12)

Normal delivery has no internal coalescing delay (formerly eight seconds). The 0.2-second worker scheduling interval, GitHub delivery, queued work, enrichment/media downloads, Discord requests and throttling still contribute. This is not an end-to-end latency benchmark or a zero-latency promise. User-configured one/five-minute alert batching and DND schedules remain intact.

The first metadata notification sends immediately. Related labels, assignees, milestones, review requests and issue types arriving within fifteen seconds of the first notification edit its existing message with the latest snapshot. This is an edit-eligibility interval, not a wait. Different families remain separate, and changes outside that interval create a new history entry. Separate comments, commits and lifecycle events such as Closed/Reopened/Merged are preserved. Existing body/comment edits continue updating their own messages. Issue-field deltas without a complete current snapshot remain separate rather than overwriting another field's update.

Per-event source selection persists before posting. Restart, failed/lost responses and older revisions preserve the same message/source and do not duplicate or overwrite newer state. DND replay uses the original webhook receipt time, not the replay time, so unrelated historical changes are not merged together. Old frozen delivery groups remain replayable. New metadata sources do not scan thread history on their first attempt; retries still recover source-tagged pages safely.

Queue.next(window_seconds) can skip an unready optional/legacy batch instead of stopping the worker on it. Default Queue.next() and the service now have no coalescing wait. Already executing HTTP requests are not preempted; retries inside such calls can still occupy the per-binding worker. This patch does not add concurrent edits to the same thread or bypass API limits.

Recommended follow-up, separate from this patch: measure webhook receipt / queue start / first Discord post / completion, yield long network retries back to the durable queue, share authorized GitHub lookups, coordinate Discord rate-limit buckets, and rehearse SQLite backup/restoration. Deployment file backups are not a replacement for operational database recovery. No live latency benchmark or production message sending was performed here.
