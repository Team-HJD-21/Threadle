# Connection language, topics and first greeting

Notification language is per repository/server binding (ko/en). The website language only seeds a new connection's default; existing stored notification language wins. Basic channel setup submits an explicit notification_language. The advanced button submits the same form with formnovalidate to /connect/team/start, preserving language without prematurely recording consent. Team settings have their own language field. /settings has a language option with Korean (KR)/English (EN) choices, and accepts KR/KO/EN when called programmatically. Only the selected binding changes. Original GitHub titles and comments are never translated. Command names/descriptions remain English. Major bot notifications support both languages, but complete production localization is not certified by these tests.

A successful new connect transaction creates a pending welcome row only if the guild/repository has no prior binding row. Existing users are not backfilled with greetings, idempotent saves do not enqueue another, and reconnected retained bindings do not enqueue again. The existing notification scheduler sends the greeting and a small snapshot (up to 3 titles per open PR/issue/discussion section) to that binding's alert channel, using durable AlertFeed receipts and phase progress across retries/restarts. A summary failure does not undo the connection or repeat the greeting. Welcome records are purged with expired connections. This reads the current open list for the sample; it does not replay old item notifications.

Creation topics now say Threadle managed channel, not GitHub Notify. The temporary token remains until the channel ID is durably saved, including recovery after a lost create response. Then a human-readable Threadle description replaces it. Existing saved layout IDs are queued for the same cleanup. Updates occur only when channel ID/guild and exact layout token/kind match, and no setup lease or unresolved creation is active. Custom topics remain untouched; completed cleanup entries do not repeatedly overwrite later edits. Permission failures are retried with cooldown without failing connection creation. Deleted layout metadata removes cleanup metadata under normal retention. No channel deletion, ID replacement, or new permissions are involved.

Validation includes lost create-response recovery, custom-topic preservation, permissions failure, welcome deduplication/summary retry, Korean/English snapshots and language isolation. Browser fixture checks cover KO/EN at 390/1440 widths, actual external-form advanced submission, CSRF/language preservation and back-link placement. Real existing-server topic migration and live Discord welcome rendering remain production checks.

Developer-facing status labels remain English in both languages (Closed, Deleted, Reopened, Merged, Draft, Approved, CI/CD Running/Succeeded/Failed), as do metadata keys such as Branches, Reviewers, Labels and Milestone. Threadle greetings, explanatory sentences and guidance follow the binding language. Issue bundle headings use the last lifecycle event (Closed/Deleted/Reopened), not Updates, while ordinary metadata changes keep Updates.
